# app

React Native + Expo (SDK 58) app, using [Expo Router](https://docs.expo.dev/router/introduction) for file-based routing. The design is in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Setup

- **Node** from `.nvmrc` (`nvm use`).
- **Android Studio**, with an emulator (Device Manager). The first build downloads the NDK, CMake and build tools it needs into the Android SDK.
- **A JDK** for Gradle. React Native recommends JDK 17; JDK 21 also works.
- `npm ci`

## Running

The app runs as a **development build**, not in Expo Go: our own native app with `expo-dev-client`, which loads its JavaScript from Metro with fast refresh.

```bash
npm run android   # build and install "Life App Dev", then start Metro
npm start         # later: just Metro, for the dev build already installed
```

Rebuild with `npm run android` only when native code changes: a native dependency is added or upgraded, or `app.config.ts` or a config plugin changes. JavaScript changes only need Metro.

A physical phone works too, over USB with debugging on. The dev build loads JavaScript from Metro at the Mac's LAN address, so the phone needs the same network, or `adb reverse tcp:8081 tcp:8081`.

### Local API

The dev variant calls the API at `http://10.0.2.2:8080`, the emulator's address for the Mac's `localhost`, so run the API locally (`api/README.md`). A physical phone can't use that address. Either run `adb reverse tcp:8080 tcp:8080` and start Metro with `API_URL=http://localhost:8080 npm start`, or set `API_URL` to the Mac's LAN address. Only the dev variant honors `API_URL`; production always uses its own URL. The URL comes from Metro's config, so changing it only needs a Metro restart, not a rebuild.

## Variants

`APP_VARIANT` selects the variant in `app.config.ts`. Both install side by side:

| Variant | `APP_VARIANT` | Package | Name | Scheme | API |
| --- | --- | --- | --- | --- | --- |
| Dev | `development` (default) | `com.lakaniemi.lifeapp.dev` | Life App Dev | `lifeapp-dev://` | `http://10.0.2.2:8080` |
| Prod | `production` | `com.lakaniemi.lifeapp` | Life App | `lifeapp://` | `https://life-app-api.lakaniemi.com` |

`npm run android:prod` builds the production variant as a release build, with the JavaScript bundled into the APK. Locally it's signed with the debug key, because the release key only exists in CI, so it's for local testing only. It can't be installed over an APK from a GitHub release; uninstall that first.

`android/` is generated by `expo prebuild` and gitignored. The build scripts regenerate it for their variant, so never edit it by hand.

## Releasing

A release is a GitHub release with the signed production APK attached as `life-app.apk`. The phones install it directly. [`releases/latest/download/life-app.apk`](https://github.com/lakaniemi/life-app/releases/latest/download/life-app.apk) always points at the newest one, and the "Update required" screen links there. The release also carries `latest.json`, a copy of `version.json` (`{ "version", "versionCode" }`) that the app fetches from [`releases/latest/download/latest.json`](https://github.com/lakaniemi/life-app/releases/latest/download/latest.json) to see whether a newer version exists.

To release, open a PR that bumps both fields in `version.json`, and merge it:

```json
{ "version": "0.0.2", "versionCode": 2 }
```

- `version` is the label people see, as `X.Y.Z`. It must be higher than the last release's.
- `versionCode` is the integer Android compares, and it refuses to install a lower one over a higher one. It must go up by at least one with every release.

The app's CI fails the PR when the bump is inconsistent. After the merge, the `app-release` workflow builds the APK, checks that it's signed with the release key, and publishes the `app-v<version>` release with notes listing the merged PRs, uploading `life-app.apk` and `latest.json` together: the release is published (and its tag created) only once both are there, so `latest.json` never announces an APK that isn't. A merge that doesn't change `version.json` releases nothing. If a run fails, fix the cause and re-run the workflow from the Actions tab: a release only exists once its tag does. A run that dies during the upload can leave an unpublished draft release behind, which is safe to delete by hand.

### Signing key (one-time setup)

Android installs an update only over an app signed with the same key, and Google sign-in is tied to the key's SHA-1. **Losing the keystore means reinstalling the app on every phone**, so keep a copy outside GitHub (it's in 1Password). Secrets in GitHub can't be read back.

```bash
keytool -genkeypair -v -keystore life-app-release.jks -alias life-app \
  -keyalg RSA -keysize 2048 -validity 10000
keytool -list -v -keystore life-app-release.jks -alias life-app   # prints the SHA-1 and SHA-256
base64 -i life-app-release.jks                                    # for the secret below
```

| Where | Name | Value |
| --- | --- | --- |
| Secret | `ANDROID_KEYSTORE_BASE64` | the keystore file, base64-encoded |
| Secret | `ANDROID_KEYSTORE_PASSWORD` | its password (a PKCS12 keystore has one, for the file and the key) |
| Secret | `ANDROID_KEY_ALIAS` | `life-app` |
| Variable | `ANDROID_RELEASE_CERT_SHA256` | the certificate's SHA-256, which the workflow compares the APK against |

The SHA-1 goes to Google's Android OAuth client for the production package, when sign-in is built (`docs/AUTH.md`).
